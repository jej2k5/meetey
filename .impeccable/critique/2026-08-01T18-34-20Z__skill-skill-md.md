## Anti-Patterns Verdict

**LLM assessment.** This does not read as machine-made in the ordinary sense — the product register rewards familiarity, and Summary → Key Decisions → Action Items is the correct, legible shape. The failure is subtler and worse: **the output could have been produced by any tool that has a transcript.** Meetey uniquely holds the audio, per-segment millisecond offsets, on-device OCR, and screen keyframes, and the artifact exploits almost none of it. The generic LLM summarization scaffold won; the thing that makes this tool different lost.

The tell is concrete. Phase 3 added `fromMs`/`toMs` to every transcript segment. The template spends them on exactly one section — Screen Content, the least likely to be challenged — and leaves Key Decisions and Action Items, the two things a reader actually needs to verify, floating with no anchor.

**Deterministic scan.** `detect.mjs --json skill/SKILL.md` → `[]`. Structurally inapplicable, not clean: the detector is an HTML/CSS rule engine and the artifact is generated Markdown, so no rule could fire. No deterministic signal is available for this target; treat the LLM assessment as unbacked by tooling here.

**Visual overlays.** None. This is a CLI tool with no viewable surface; no server was started and no injection attempted.

## Overall Impression

The bones are right and the restraint is real — four sections, no decoration, honest empty states. But the artifact is organized around what the pipeline produces rather than what the reader needs. The single biggest opportunity: **make the notes verifiable.** Right now a user who doubts one line of the summary has exactly one recourse — read 9,000 words of unpunctuated ASR. Timestamped claims would collapse that to a glance, and the data to do it already exists.

## What's Working

- **Restraint in the section set.** Four sections, no scaffolding, no eyebrows, no invented structure. Many meeting tools bury the useful part under "Sentiment" and "Topics." This doesn't.
- **Truncation is surfaced honestly.** "Never present a truncated capture as complete" in the skill is exactly right, and rare. Most tools silently ship a partial artifact.
- **Escalation model for keyframes.** OCR first, read the image only when the text is insufficient. Cost-aware and privacy-aware without asking the user to think about it.

## Priority Issues

**[P1] The transcript dominates the artifact it's supposed to support**
- *Why it matters:* A 60-minute meeting is ~9,000 words of unpunctuated, unattributed ASR sitting under a `###` heading of the same weight as Action Items. Every subsequent visit to the file — to check one task — scrolls through it. The skill also prints it into chat, so the user reads it twice.
- *Fix:* Write the transcript to a sibling file (`<session>-transcript.md`) and link it, or wrap it in `<details>`. Never print it in chat; report its path instead.
- *Suggested command:* `/impeccable distill`

**[P1] Decisions and action items have no timestamp**
- *Why it matters:* These are the two claims a reader will want to verify, and they're the only ones with no way back to the source. The `segments` array already carries `fromMs`/`toMs` for every utterance — the capability shipped and went unused.
- *Fix:* Anchor each decision and action item with `[mm:ss]`, matching the Screen Content convention already in the template.
- *Suggested command:* `/impeccable layout`

**[P1] No signal about transcription quality**
- *Why it matters:* `base.en` on a noisy call produces garbage, and the summary is generated from that garbage in the same confident voice as a clean one. The user cannot distinguish a reliable summary from a hallucinated one without reading the transcript — the exact thing the summary exists to avoid. This is a trust failure on the core deliverable.
- *Fix:* Surface the model used, and a cheap quality heuristic (proportion of very short or repeated segments, average segment confidence). When it's poor, say so at the top and recommend `MEETEY_MODEL=small.en`.
- *Suggested command:* `/impeccable harden`

**[P2] Machine formats in a human document**
- *Why it matters:* `Recorded:` renders `new Date().toISOString()` — `2026-08-01T14:02:11.123Z → 2026-08-01T14:47:03.556Z`. It omits the one derived fact a reader wants (duration) and reads as a log line. Filenames are epoch integers, so browsing past meetings is impossible without grep.
- *Fix:* `Fri 1 Aug 2026, 2:02–2:47 PM (45 min)`. Add a human date to the filename or a front-matter title.
- *Suggested command:* `/impeccable clarify`

**[P2] Empty states report absence without diagnosing it**
- *Why it matters:* "No explicit decisions recorded" is true in two very different worlds: the meeting was a status update, or the transcript was too poor to extract anything. The second is actionable — switch models — and the copy can't distinguish them.
- *Fix:* Branch the copy on transcript quality. Teach the next step when the cause is fixable.
- *Suggested command:* `/impeccable onboard`

## Persona Red Flags

**Alex (Power User):** Wants action items in a task system, not a checkbox in a file he'll never reopen. No export, no consolidated "open items across all meetings" view, no way to request a different output shape without re-prompting. Gets a 9,000-word wall printed into his terminal after every call.

**Riley (Stress Tester):** Records a 3-hour meeting — no warning that `base.en` will degrade badly over that length, no duration cap. Records a meeting with a non-English speaker; transcription is hardcoded to `-l en` and returns confident nonsense with no flag. Records 45 minutes of silence; gets a summary with the same structural confidence as a real one.

**Casey (Distracted Mobile):** Opens notes on her phone the next morning. The file leads with a good summary, then buries the two action items assigned to her below a wall of raw transcript. Scrolls, gives up, asks in chat instead.

## Minor Observations

- Timestamp formats disagree within one document: ISO in the header, `mm:ss` in Screen Content.
- No attendee list. Names are usually spoken in the transcript and never extracted.
- The Screen Content bullet asks for two things at once ("what was on screen, and how it related to the discussion"), which reliably produces run-on bullets.
- Chat output duplicates the file in full, including the transcript. The file is the artifact; chat should be the receipt.
- Nothing in the output points at the README's troubleshooting table when transcription fails.

## Questions to Consider

- What if every claim in the summary carried its timestamp, and the transcript became a linked appendix rather than a section?
- Should a low-confidence transcript produce a *different shaped* document — one that leads with "quality was poor, here's what I could extract" — rather than the same template with weaker content?
- What does this artifact have that Otter and Granola don't? Right now the answer is "it ran locally." Should the answer be "every line is anchored to the second it was said, and to what was on screen at that moment"?
- Who reads this file a week later, and what are they looking for? The current structure optimizes for the first five minutes after a meeting.
